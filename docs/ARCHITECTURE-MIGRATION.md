# 架构迁移评估：从零框架原生单体到工程化前后端分离

> 评估对象：三磊·车邻汇客户订货系统（当前仓库）
> 评估基线：2026-10-24 代码状态；全量功能校验 77/77 通过
> 估算口径：1 名熟练全栈工程师的**有效工时（人天）**，含自测与代码评审，不含需求变更、等排期、线上故障处理；误差约 ±20%

---

## 1. 摘要

| 项目 | 结论 |
| --- | --- |
| 当前形态 | 接口级前后端分离，技术上为零框架、零第三方依赖的原生单体 |
| 推荐目标 | Fastify + Drizzle(SQLite) + Vue 3/Vite 管理端 + 原生小程序 + CI，**保持 API 契约不变** |
| 推荐方案 | **方案 B（分两期：B1 后端框架化 → B2 管理端工程化）** |
| 总工时 | B 方案 **52–62 人天**；若同时升级 PostgreSQL（方案 C）**68–85 人天** |
| 风险等级 | 中低（API 契约冻结 + 黑盒回归可兜底）；最大风险是管理端重写的回归量 |
| 不建议动的部分 | 自研 `xlsx.js`/`wechat.js`、小程序、业务规则本身 |

**核心判断**：这不是一次"重写系统"，而是一次"换骨架、保行为"的迁移。现有 77 项接口校验和 12 项单元测试是黑盒性质，可以直接作为迁移验收闸门，这是本项目最大的迁移优势。

## 2. 现状基线（量化）

| 维度 | 数值 | 说明 |
| --- | --- | --- |
| 后端代码 | 4,593 行 / 163 个函数 | `server/` 11 个文件 |
| HTTP 端点 | ~80 个（75 个 JSON 响应 + 5 个文件下载） | `routes.js` 46 个精确匹配 + 28 个正则匹配 |
| 数据访问 | 220 处 `db.prepare` | business 93 / admin 38 / operations 36 / csv 14 / database 14 / core 12 / routes 13 |
| 数据库 | 26 张表 / 11 个索引 / 35 个外键 | SQLite（WAL）+ 单文件 |
| 第三方依赖 | **0 个** | 无 Express/Koa/ORM/前端框架/构建工具/Excel SDK |
| 管理端 | 1,898 行 / 15 个页面 / 24 个弹窗 / 49 处 API 调用 | 原生 JS + `innerHTML`，无构建 |
| 小程序 | 2,080 行 / 12 个页面 / 31 处请求 | 微信原生，无跨端框架 |
| 测试 | 12 项单元测试 + 77 项全量校验 | 以 HTTP 黑盒为主 |
| 部署 | 单 Docker 容器 + Caddy 反代 | 静态页面与 API 同进程 |

### 当前架构的关键技术约束

1. **数据库访问是同步的**：`node:sqlite` 的 `DatabaseSync` + `withTransaction(db, fn)` 同步事务。若换成异步驱动（PostgreSQL/MySQL），163 个函数、80 个端点会产生"异步传染"，这是迁移成本的第一大头。
2. **路由层手写**：URL 解析、错误码、CORS、4MB 限制、原始报文（微信回调）、文件下载都直接操作 `req/res`。
3. **管理端是字符串模板渲染**：15 个 `renderX()` 直接拼 HTML 再绑定事件，没有组件、状态库、路由库。
4. **静态资源与 API 同进程**：`serveStatic` 处理非 `/api` 路径，部署上不分离。

## 3. 目标架构

```
                    ┌──────────────────────────────┐
  浏览器 ──────────▶│  admin (Vue 3 + Vite)         │──┐
                    └──────────────────────────────┘  │  HTTPS /api (Bearer)
                    ┌──────────────────────────────┐  │
  微信小程序 ──────▶│  miniprogram（原生，保持不变） │──┤
                    └──────────────────────────────┘  │
                    ┌──────────────────────────────┐  ▼
  未来 ERP/App ────▶│  契约：OpenAPI / JSON Schema  │  Fastify API
                    └──────────────────────────────┘  ├─ plugins: db/auth/errors/cors/rate-limit
                                                       ├─ routes: 12 个资源插件
                                                       ├─ services: 现有 business/admin/operations
                                                       └─ repositories: Drizzle(SQLite)
```

### 技术选型建议与理由

| 层 | 推荐 | 备选 | 理由 |
| --- | --- | --- | --- |
| 后端框架 | **Fastify 5** | Express 5 / NestJS | 原生 async、JSON Schema 校验可替代手写参数校验、插件化拆分 80 个端点、性能与生态均衡；NestJS 只有在团队已重度使用时才值得，否则装饰器/DI 会额外增加 30% 工时 |
| ORM/查询层 | **Drizzle ORM（SQLite）** | Kysely / Prisma | Drizzle 贴近 SQL、可按模块渐进替换 220 条查询、同一套 schema 后续可切 PostgreSQL |
| 数据库 | **先保持 SQLite**，二期再评估 PostgreSQL | PostgreSQL | 一期不碰存储可规避异步改造、数据迁移、运维升级三大风险 |
| 管理端 | **Vue 3 + Vite + Pinia + Element Plus** | React + Ant Design | 现网是中文后台、表格/表单密集，Element Plus 组件覆盖度高；可复用现有 308 行 CSS 与交互规范 |
| 小程序 | **保持原生** | uni-app/Taro | 12 个页面已稳定，重写无业务收益 |
| 测试 | Node `node:test` + Playwright | Vitest | 保留 12 项单测；新增 Playwright 覆盖 7 角色 × 15 页 |
| 工程化 | pnpm workspace + ESLint + Prettier + GitHub Actions | 单体仓库目录化 | 轻量 monorepo 即可，不必上 Nx/Turborepo |

**迁移后的目录建议**

```
apps/
  api/                  # Fastify
    src/plugins/        # db, auth, errors, cors, rate-limit
    src/routes/         # customers/orders/plans/... 12 个插件
    src/services/       # 现 business/admin/operations
    src/repositories/   # Drizzle 查询
  admin/                # Vue 3 + Vite
  miniprogram/          # 原生，保持不变
packages/
  shared/               # 请求/响应 schema、枚举、类型
  db/                   # schema + migrations
docs/
```

## 4. 方案对比

| 方案 | 范围 | 工时 | 收益 | 风险 | 适用 |
| --- | --- | --- | --- | --- | --- |
| **0. 只做工程化** | 不换框架：拆路由文件、抽 service、JSDoc + `tsc --checkJs`、ESLint、CI | **6–10 人天** | 可维护性明显提升，零运行时风险 | 低 | 预算极紧、只解决"文件太大" |
| **A. 仅后端框架化** | Fastify + 保持 SQLite/原生 admin/小程序 | **18–26 人天** | 路由、校验、错误、限流标准化；接口契约可生成 | 低 | 先解决后端，前端二期 |
| **B. 前后端工程化（推荐）** | A + Drizzle + Vue3 管理端 + 静态分离 + CI | **52–62 人天** | 真正的前后端工程化与独立部署 | 中（管理端回归） | 有 2–3 个月迭代计划 |
| **C. 完全分离** | B + PostgreSQL + Redis（会话/限流）+ 独立部署 | **68–85 人天** | 可多实例、可扩容、可审计升级 | 中高（异步改造 + 数据迁移） | 多租户/高并发预期 |
| **D. 企业级** | C + NestJS + React + monorepo + RBAC 重构 | **78–95 人天** | 组织级规范 | 高 | 团队 > 5 人、长期平台化 |

> 若目标是"先让代码能长期维护、不急于换 UI"，选 A；若目标是"交付一个标准的前后端分离工程"，选 B；PostgreSQL 建议放到 B 稳定运行 1–2 个迭代后再做 C，不要和框架迁移同批上线。

### 方案 C 的增量（在 B 之上）

| 增量项 | 工时 | 说明 |
| --- | --- | --- |

## 6. 实施路线（推荐 B 分两期，可独立上线）

### 阶段 P0：契约冻结与基线（2–3 人天）

- 把 80 个端点的请求/响应固化为 JSON Schema/OpenAPI；生成 `docs/openapi.json`。
- 将 `scripts/verify-api.mjs`（77 项）与 `test/api.test.js`（12 项）接入 CI，作为**唯一验收闸门**。
- 前端接口调用清单化（管理端 49 处、小程序 31 处），确认无隐藏契约。

**交付**：OpenAPI 文档 + CI 红灯基线（当前应全绿）。

### 阶段 P1：后端框架化（12–18 人天，覆盖模块 1–4、6、7，是方案 A 的主体）

- Fastify 骨架、错误处理、CORS、限流、静态/下载适配。
- 逐资源迁移路由：customers → products → prices → inventory → suppliers → orders → plans → payments → finance → shortages → after-sales → users → imports/exports。
- 采用绞杀者模式：未迁移的路径先代理到旧 handler（或新旧双端口并存，Caddy 按路径切流）。
- 每迁移 1 个资源，跑一遍 77 项校验。

**交付**：新 API 与旧 API 行为一致；管理端、小程序零改动；可随时回滚（切回旧容器）。

### 阶段 P2：数据访问 ORM 化（与 P1 部分重叠，6–10 人天）

- Drizzle schema 与 220 条查询按模块替换；先读后写、先简单后复杂。
- 保留缺货加权分配、计划执行率等复杂 SQL 为 `sql` 片段，不强求 ORM 化。

### 阶段 P3：管理端工程化（18–24 人天）

- Vue3 脚手架、路由、Pinia、请求层、权限菜单（复用 `navigation` 配置）。
- 公共组件：表格、分页、筛选、弹窗表单、状态徽章、金额/日期格式化、Toast。
- 按页面迁移顺序：登录/概览 → 客户/产品/价格 → 订单/计划 → 库存/缺货/供应商 → 收款/财务/售后 → 报表/账号/导入导出。
- 每页迁移后用 Playwright 对比旧版截图与关键交互。

**交付**：可逐页灰度（`/legacy` 保留旧版入口），每页可独立上线。

### 阶段 P4：部署分离与 CI（3–5 人天）

- `admin` 构建产物由 Nginx/CDN 托管；API 独立容器；Caddy 仅反代 `/api`。
- GitHub Actions：lint → 单测 → 77 项校验 → Playwright → 构建镜像。
- 备份：SQLite 在线备份（保留 WAL/SHM）或 `pg_dump`（若 C）。

### 阶段 P5（可选）：PostgreSQL 升级（15–23 人天）

- 在 B 稳定运行后单独立项；先异步改造 + 双写校验，再切读、切写、下线旧库。

## 7. 风险登记册

| # | 风险 | 概率 | 影响 | 对策 |
| --- | --- | --- | --- | --- |
| 1 | 同步 DB → 异步驱动的"异步传染" | 方案 C 高 / B 无 | 高 | B 阶段保持 SQLite（同步），异步改造单独立项；先加测试再改签名 |
| 2 | 微信回调原始报文被框架解析破坏 | 中 | 高 | Fastify `addContentTypeParser(..., { parseAs: 'buffer' })`；保留 `readText` 语义；用生成密钥对做单测 |
| 3 | 金额精度（`REAL` → `numeric`） | 中 | 高 | 统一走 `money()`；新增金额汇总回归（订单/收款/发票） |
| 4 | 时间与月份统计依赖 SQLite 方言 | 中 | 中 | `substr(created_at,1,7)`、`julianday` 逐条改写；报表回归 |
| 5 | 管理端 15 页视觉/交互回归 | 高 | 中 | 逐页迁移 + 截图对比 + 7 角色权限矩阵；保留旧版入口灰度 |
| 6 | 权限矩阵被打破 | 中 | 高 | 保留现有 77 项中的 8 项越权断言，扩展为每角色 × 每端点 |
| 7 | 会话/限流内存态在多实例失效 | 方案 C 高 | 中 | 单实例优先；多实例时 Redis 或粘性会话 |
| 8 | 静态资源路径穿越/缓存策略变化 | 低 | 中 | Nginx `root` 限定 + 禁 dotfile；保留 HEAD/缓存头测试 |
| 9 | 中文文件名下载（Content-Disposition） | 低 | 低 | 下载类接口逐一回归 |
| 10 | Node 版本约束（`node:sqlite` 需 ≥24） | 中 | 低 | 锁 `engines`；或换 `better-sqlite3` 支持 LTS |

## 8. 不建议迁移的部分

| 模块 | 原因 |
| --- | --- |
| `server/xlsx.js`（267 行，基于 `zlib` 自研） | 无依赖、行为已验证；换 SheetJS 只会增加包体与新风险 |

| 小程序（12 页） | 接口契约不变即可零改动；重写无业务收益 |
| 业务规则（价格优先级、预付款、缺货加权、计划限量） | 已被 77 项校验覆盖，重写风险远大于收益；只改"怎么取数"，不改"怎么算" |

## 9. 验收标准（迁移完成的定义）

1. `scripts/verify-api.mjs` **77/77** 通过（对旧版与新版的响应逐项一致）。
2. `node test/api.test.js` **12/12** 通过。
3. Playwright：7 个角色 × 各自可见页面全部渲染成功、无 JS 异常、无 `undefined/NaN`；24 个弹窗可打开。
4. 小程序 12 条主流程（登录→选品→购物车→下单→支付→计划→售后→退出）通过开发者工具回归。
5. 微信支付 mock 流程、Excel 导入导出、下载文件名、CORS、目录穿越、8 次失败限流逐项回归。
6. 性能不劣化：关键列表接口 p95 与旧版持平（±10%）。
7. 部署：静态与 API 可独立发布；回滚时间 < 5 分钟。
